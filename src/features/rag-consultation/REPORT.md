# 4번 기능 「파일 기반 RAG 상담」 개발 정리 보고서

- 작성 기준일: 2026-11-02 · 브랜치: `feat/rag-consultation` (main 미변경)
- 모든 학원·원생·금액은 테스트용 **가상 데이터**입니다. 아래 수치는 이 브랜치에서 실제로 실행한 결과입니다.
- 엔진 규칙은 직접 보완하지 않았습니다. 기술 조사 문서(`4. 파일 기반 RAG 상담 기술 조사`)의 검색 기법만 적용해 비교했습니다. 앞서 중학생 질문 실패를 보고 넣었던 유사어·라우팅 보완은 되돌렸습니다.

## 요약

1. **개발 범위**: 학원 문서와 원생 분석 리포트를 근거로 답하고, 근거를 인용하고, 자료가 없으면 지어내지 않고 보류하는 **서버 모듈 전체**를 만들었습니다(코드 약 9,000줄, 테스트 249개).
   - 이번에 기술 조사 문서의 검색 기법 5가지를 **바꿔 끼울 수 있는 순위 전략**으로 추가했습니다: Kiwi 형태소 BM25, 로컬 임베딩, Hybrid RRF, 로컬 재정렬, 점수 기반 보류.
   - 실제 DB·로그인·서버 배포·외부 생성 API·PDF/HWPX 파싱은 **연결 지점만 만들고 구현하지 않았습니다**.
2. **중학생 표현 100문항 실험(RAG만 vs 기술 적용)**: 같은 저장소·같은 권한 필터에서 순위 전략만 바꿨습니다.
   - **검색 품질**: 정답 문서가 1위인 비율 **37.6% → 81.2%**, 5위 안 **71.8% → 97.6%**. 거의 전부 재정렬 모델 덕분입니다.
   - **RAG 답변**(1위 청크를 그대로 답으로 사용): **12/100 → 36/100**. 점수 기반 보류를 더하면 **46/100**이고, 틀린 답이 64개에서 31개로 줄었습니다.
   - **상담 엔진에 꽂았을 때**: 60 → 58~61/100으로 **거의 변화 없음**. 엔진의 오답 대부분은 검색이 아니라 질문 해석(라우팅)에서 나오기 때문입니다.
   - **비용**: 재정렬 모델은 이 컨테이너 CPU에서 검색 1회당 약 1.4초(BM25는 2ms)가 걸리고, 모델 파일이 약 570MB입니다.
3. **사전 문서**: 가상 학원 3곳의 운영 문서 36개와 원생 리포트 48개(총 84개), 정형 사실 645개, 평가 질문 90개, 중학생 표현 질문 100개를 준비했습니다. 받은 지시서·기술 조사·프로젝트 기준·합성 평가자료 81건도 함께 썼습니다.
4. **문제점**:
   - 처음 보는 말투를 규칙이 잘못 읽는 문제가 가장 큽니다(엔진 60/100). 검색 기법으로는 해결되지 않습니다.
   - 재정렬 모델은 엔진이 만든 키워드 질의를 받아 오히려 3문항을 틀렸고, CPU 비용이 큽니다.
   - 평가 자료를 직접 만들었습니다. 운영 연동(DB·인증·배포·생성 API)도 하지 않았습니다.

## 1. 개발 범위

### 1.1 무엇을 만들었나

질문을 받으면 아래 순서로 처리하는 **독립 서버 모듈**(`src/features/rag-consultation/server`)입니다. 표준 `Request → Response` 핸들러라서 정해지지 않은 백엔드에 붙일 수 있습니다. 현재 앱은 정적 export여서 앱 안에 서버를 둘 수 없습니다.

```text
요청 검증 → 서버 세션으로 권한 범위 계산
 → 질문 해석(규칙): 학생·반·단원·기간·금액·부정/비교 표현·보안 신호
 → 보안 차단: 다른 학원·전체 학생 명단·권한 밖 학생 → 거부
 → 학원 정보: 수강료·시간표·강사·모집·휴보강 = 정형 사실 조회(생성 0회)
              환불·셔틀·시설 등 = 승인 문서의 해당 절·표 칸 인용(생성 0회)
 → 학습 분석: 정답률·취약 영역·기간 비교(생성 0회), 원인·태도·예측 요청은 보류
 → 학습 방향: 강사가 확인한 학습 방향이 있으면 인용, 없을 때만 생성 1회(장애 시 담당자 연결)
 → 사후 검사: 인용 재확인, 답변 숫자가 근거에 있는지, 다른 학생 이름·코드가 섞이지 않았는지

검색 단계 = [권한·승인·유효기간 필터로 후보 확정] → [순위 전략] ← 이번에 교체 가능하게 만든 부분
```

### 1.4 구현하지 않은 것(범위 밖 또는 차단 요소)

- **운영 DB·로그인 연동·서버 배포**: 저장소에 대상이 없습니다. 지금은 메모리 저장소라서 재시작하면 색인이 사라집니다.
- **외부 생성 API 실연동**: 키와 공급자가 정해지지 않아 **검증하지 않았습니다**. 테스트는 mock으로만 했습니다.
- **PDF·DOCX·HWPX·스캔 파싱**: 현재는 텍스트/Markdown 표만 읽습니다.
- **기술 조사의 나머지 기법**: KURE-Sparse/Reranker-nano(ONNX 배포본이 없어 변환 필요), 점수 융합 분류기(라벨링 필요), Parent–Child, GraphRAG·Self-RAG(P2·P3)는 적용하지 않았습니다.

## 2. 중학생 표현 100문항: RAG만 vs 기술 조사 기법 적용

### 2.1 질문 세트

- 파일: `server/__fixtures__/academies-v1/eval/middle-school-paraphrase.jsonl`
- **100문항**: 답할 수 있는 질문 85개 + 문서에 없어서 보류해야 하는 질문 15개
  - 학원별: 가온수학 55개 · 새솔영어 45개(다온입시는 고등부라 제외)
  - 계정: 중학생 3명, 비회원 방문자 2명. 기준일: 2026-11-02 ~ 11-20
- **16개 유형**: 수강료 12, 시간표 11, 정답률 10, 휴보강 9, 강사 5, 취약 영역 5, 셔틀 5 외
- **유사어 107개**를 섞었습니다. 문서의 공식 표현 대신 중학생이 쓸 법한 말입니다.
  - 학원비·원비·깎아줘, 쌤·샘·담당샘, 보충(=보강)·학원 쉼·노는 날
  - 공부방·자습하는 방, 봉고·학원 버스, 레테·들어가기 전에 보는 시험, 몇 퍼·월말 시험
- **함정**: 채점 수정본(r1→r2), 아직 적용 전인 변경 시간표, 2027년 개정 수강료, 셔틀 1회차/2회차 열 혼동, 아직 발행되지 않은 11월 리포트, 미승인 초안 금액.
- **작성 방식**: 엔진 코드를 보지 않고 학원 문서만 보고 작성했습니다. 작성 후 스크립트로 두 가지를 확인했습니다.
  - 모든 정답 문구가 해당 문서에 실제로 있는지
  - 정답 문서가 그 날짜에 승인·유효하고, 리포트는 본인 것인지
  - 사람 검수와 실제 학생 질문 수집은 하지 않았습니다(2.7 한계).

### 2.2 적용한 기술(기술 조사 문서 기준)

| 구성   | 기법                                                   | 조사 문서 위치 | 설정                                                                                                   |
| ------ | ------------------------------------------------------ | -------------- | ------------------------------------------------------------------------------------------------------ |
| **R0** | BM25(단어 + 한글 2-gram) — **기준선(RAG만)**           | 5.1절          | 지금까지 쓰던 기본값                                                                                   |
| R1     | BM25(Kiwi 형태소 + 사용자 사전)                        | 5.1절, E03/E25 | kiwi-nlp 0.24.1(CoNg 모델). 명사·동사 어간·어근만 사용. 사용자 사전은 반 이름·별칭·단원·유형(카탈로그) |
| R2     | Dense 임베딩 단독(참고용)                              | 5.2·5.4절      | `multilingual-e5-small` q8, `query:`/`passage:` 접두어, 허용 후보 안 정확 코사인 계산                  |
| R3     | Hybrid RRF(R0 + R2)                                    | 5.3절, E04     | k = 60(조사 문서의 초기값)                                                                             |
| R4     | Hybrid RRF(R1 + R2)                                    | 5.3절          | k = 60                                                                                                 |
| R5     | R4 상위 20개 → Cross-Encoder 재정렬                    | 6절, E07       | `bge-reranker-v2-m3` q8(6.2절 후보). KURE-Reranker-nano는 ONNX 배포본이 없어 제외                      |
| +보류  | 검색 점수 기반 보류: 1위 점수 절대값 / 1·2위 상대 간격 | 0절 10번, E18  | 임곗값은 **dev 56문항에서만** 고르고 test 44문항으로 확인                                              |

- E32(임베딩 입력 512토큰 상한) 확인: 색인한 청크 465개 중 **잘린 것 0개**.
- 엔진 규칙·사전은 이 실험에서 **바꾸지 않았습니다**.

### 2.3 비교 방법

- 모든 구성이 **같은 저장소, 같은 권한·승인·유효기간 필터**를 씁니다. 바뀌는 것은 허용된 후보의 순서뿐입니다.
- 세 가지를 측정합니다.

| 측정                   | 방법                                                              | 맞았다고 보는 기준                                                                          |
| ---------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **검색 품질**(85문항)  | 질문 원문으로 상위 10개 검색                                      | 정답 문서가 1위(hit@1) / 3위 안(Recall@3) / 5위 안(Recall@5), MRR@10                        |
| **RAG 답변**(100문항)  | 1위 청크 원문을 그대로 답으로 사용. 생성 모델 없음                | 1위가 정답 문서이고 정답 문구를 모두 포함, 금지 문구 없음. 보류 질문은 보류하면 정답        |
| **상담 엔진**(100문항) | 같은 순위 전략을 엔진에 꽂음(규칙 라우팅·정형 조회·검증은 그대로) | 상태 `answered` + 정답 문구 전부 + 금지 문구 없음 + 정답 문서 인용. 보류 질문은 답하지 않음 |

- 정답 문서에는 `also_valid_source_ids` 3건이 포함됩니다. 질문 작성자가 결과를 보기 전에 notes에 "같은 문구가 다른 문서에도 있음"이라고 적어 둔 경우입니다.
- dev/test는 결과를 보기 전에 문항 ID의 해시(sha256)로 나눠 고정했습니다. 이 실험에서 dev를 쓰는 곳은 보류 임곗값 선택뿐입니다.
- 시간은 이 컨테이너(CPU 4코어, GPU 없음)에서 잰 값입니다. 배포 서버 성능이 아닙니다.

### 2.5 해석

- **재정렬이 검색 개선의 대부분입니다.**
  - hit@1 37.6% → 81.2%, Recall@5 71.8% → 97.6%. 조사 문서 6절의 기대(상위 후보 정밀 재정렬)와 같은 방향입니다.
  - 대가는 CPU 시간입니다. 검색 1회가 2ms에서 약 1.4초가 됩니다. 조사 문서도 "CPU 지연 실측 필수"라고 했던 부분입니다.
- **Hybrid RRF는 이 자료에서 Dense 단독보다 낮았습니다.**
  - R3 hit@1 50.6% < R2 55.3%. BM25가 중학생 말투에서 약해서, 같은 비중으로 섞으면 Dense의 좋은 순위가 희석됩니다.
  - 조사 문서의 "Hybrid가 보통 유리"는 이 자료에서는 확인되지 않았습니다. 가중치 조정은 튜닝이라 하지 않았습니다.
- **Kiwi 형태소는 효과가 엇갈립니다.**
  - Recall@3은 62.4% → 69.4%로 올랐지만 hit@1은 37.6% → 36.5%로 비슷하거나 낮습니다.
  - dev에서는 좋아지고 test에서는 나빠져(MRR 0.498 → 0.594 / 0.552 → 0.454) 판단하기 어렵습니다.
- **점수 기반 보류는 틀린 답을 줄이지만, 답할 수 있는 질문도 버립니다.**
  - R5 + 절대값 보류: 틀린 답 64 → 31개, 대신 답할 수 있는 23개를 보류. test에서도 18/44(보류 없음 13/44)로 유지됐습니다.
  - BM25(R0·R1)는 점수 범위가 질문마다 달라 보류 규칙이 질문 대부분을 버립니다(54~72개).
  - 1·2위 간격 규칙은 Dense·RRF 점수에서는 쓸 만한 임곗값을 찾지 못했습니다.
- **"맞는 문서를 찾는 것"과 "답하는 것"은 다릅니다.**
  - R5는 85문항 중 69개에서 정답 문서를 1위로 찾았지만, 1위 청크에 정답 문구가 있는 것은 36개입니다.
  - 33개는 문서는 맞지만 다른 행·다른 반·다른 기간을 가리켰습니다(정답률 7, 수강료 4, 시간표·강사·휴보강·셔틀 각 3 등).
  - 예: "우리 반 학원비 얼마?"에서 BM25·재정렬 모두 수강료 문서를 1위로 찾지만, 서버가 아는 "우리 반"의 행을 고르지는 못합니다.
  - 그래서 가장 좋은 RAG(R5 + 보류, 46/100)도 정형 조회를 하는 엔진(60/100)보다 낮습니다.
- **엔진은 검색 기법으로 거의 바뀌지 않습니다.**
  - 엔진은 대부분 규칙 라우팅과 정형 사실로 답하고, 검색은 시설·셔틀·환불 같은 절 인용에만 씁니다.
  - 엔진 오답 40개의 원인은 대부분 질문 해석입니다("보충"을 학습 상담으로 오인, "학원 쉼" 미인식 등). 검색 순서를 바꿔도 고쳐지지 않습니다.
  - **R5가 엔진에서 3문항을 새로 틀린 이유**: 엔진은 검색할 때 사용자 원문이 아니라 자체 키워드 묶음(예: "운영 시간 운영시간 문열 일요일")을 질의로 씁니다. 재정렬 모델은 자연어 질문을 기대하므로 엉뚱한 절을 올렸습니다.
    - MS-035 "일요일에도 문 열어요?": 운영 시간 절 대신 상담 안내 절
    - MS-082 "레테 평일엔 몇 시?": 학원 소개의 레벨테스트 절 대신 모집 현황의 등록 절차
    - MS-086 "어디 있어요? 몇 층?": 위치 절 대신 시설 현황 절
    - 재정렬에 사용자 원문을 넘기도록 포트를 바꾸면 고칠 수 있을 가능성이 큽니다. 엔진 변경이라 이번에는 하지 않았습니다(4.3).

### 2.6 이전 실험과의 관계

- 직전에는 dev 실패를 보고 유사어·라우팅 규칙을 직접 넣어 엔진을 60 → 87/100(test 29 → 32/44)으로 올렸습니다.
- 요청에 따라 그 보완은 **되돌렸고**, 이번 엔진 기준선(R0, 60/100)은 그 이전 상태와 같습니다.
- 검색 기법과 규칙 보완은 고치는 대상이 다릅니다. 검색 기법은 "맞는 문서 찾기"를, 규칙 보완은 "질문 해석"을 고칩니다.

### 2.7 한계

- 질문은 문서를 보고 **AI가 작성**했습니다. 실제 중학생 질문 로그도 아니고 사람이 검수하지도 않았습니다.
- RAG 답변 측정에는 생성 모델이 없습니다(1위 청크 원문 = 답). 상위 3개를 완벽하게 읽는 생성 모델을 가정하면 R0 31개 → R5 53개(85문항 중)까지가 상한입니다. 키가 없어 실제 생성은 **측정하지 않았습니다**.
- 학원 2곳·100문항(test 44개)은 작은 표본입니다. 보류 임곗값은 dev 56문항으로 골랐습니다.
- 시간은 이 컨테이너 CPU 기준입니다. 배포 서버의 CPU·RAM은 아직 모릅니다.

### 4.2 문제점(중요한 순서)

1. **처음 보는 말투를 규칙이 잘못 읽습니다(엔진 60/100).**
   - 주제 판별이 규칙 사전에 의존합니다. "보충"(보강), "학원 쉼"(휴강), "봉고"(셔틀), "쌤이 뭐 하라고"(학습 방향) 같은 말을 놓치거나 다른 주제로 보냅니다.
   - 검색 기법은 이 문제를 고치지 못합니다(엔진 60 → 58~61).
2. **재정렬 모델의 비용과 연결 방식**:
   - CPU에서 검색 1회 약 1.4초(p95 2초), 모델 약 570MB입니다. 배포 서버 사양이 확인되기 전에는 기본값으로 쓰기 어렵습니다.
   - 엔진은 사용자 원문 대신 키워드 묶음으로 검색하기 때문에, 재정렬을 그대로 꽂으면 오히려 3문항이 나빠졌습니다.
3. **RAG만으로는 "우리 반", 날짜, 반별 값 같은 정형 질문을 못 맞힙니다.** 문서는 맞게 찾아도 행·반·기간이 다릅니다(R5: 문서 1위 69개 중 답 포함 36개).
4. **보류 규칙의 대가**: 점수 기반 보류는 틀린 답을 절반으로 줄이지만, 답할 수 있는 질문을 23개 버립니다. BM25 점수로는 보류 기준을 잡기 어렵습니다.
5. **평가가 독립적이지 않습니다.** 문서·질문·정답을 이 작업에서 만들었고, 가상 학원 90건은 규칙을 다듬는 데 썼습니다. 실제 학생 질문도 아니고 사람 검수도 없습니다.
6. **운영 연동을 하지 않았습니다.**
   - 메모리 저장소(재시작 시 소실, 다중 인스턴스 호출 제한 미지원)
   - DB·로그인·서버 배포 없음, 생성 API 실연동 미검증, PDF/HWPX 미지원

### 4.3 제안(결정이 필요한 것 포함)

1. **재정렬에 사용자 원문을 넘기기(엔진 변경, 승인 필요).** 검색 포트에 "원래 질문" 필드를 추가해 재정렬은 원문으로, BM25는 엔진 키워드로 하게 합니다. 2.5의 3문항 회귀가 사라지는지 같은 100문항으로 확인합니다.
2. **엔진이 주제를 못 정한 질문에만 R5 검색 + 점수 보류를 쓰기(조사 문서 8.3절 "조건부 검색 확장", 승인 필요).** 규칙이 실패한 질문만 검색으로 넘기므로 정형 질문의 정확도는 유지됩니다. 비용은 그 질문에만 듭니다.
3. **배포 서버 사양 확인 후 기본 구성 결정**:
   - CPU만 있는 작은 서버: Dense 단독(R2, 검색 1회 약 6ms, hit@1 55%)이 비용 대비 효과가 좋습니다.
   - 여유가 있으면: 재정렬(R5)을 조건부로(상위 후보 점수 간격이 작을 때만) 적용합니다(조사 문서 6.1절 5번).
   - KURE-Reranker-nano(149M)는 ONNX로 변환하면 bge(568M)보다 가벼울 수 있어 비교할 가치가 있습니다.
4. **질문 해석 개선 방법 결정**: 규칙 사전을 운영 로그로 보강할지, 로컬 임베딩 기반 주제 분류(조사 문서 P1)를 붙일지 팀이 정합니다.
5. **평가를 독립적으로 다시 합니다.** 실제 중학생·보호자 질문을 수집하고, 사람이 정답을 검수하고, 처음 보는 학원 자료로 다시 측정합니다.
6. **운영 연동**: 실제 DB·로그인 정보로 포트(`AccessScopePort`, `ApprovedFactsPort`, `RagDocumentsPort`)를 구현합니다. 그다음 생성 공급자의 약관(미성년 이용·국외 처리)을 검토하고, 실제 문서 형식(PDF/HWPX) 비율을 확인합니다.
