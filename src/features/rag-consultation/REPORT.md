- 작성 기준일: 2026-11-02 · 브랜치: `feat/rag-consultation` (main 미변경)
- 모든 학원·원생·금액은 테스트용 **가상 데이터**입니다. 아래 수치는 이 브랜치에서 실제로 실행한 결과입니다.

## 요약

1. **개발 범위**: 학원 문서와 원생 분석 리포트를 근거로 답하고, 근거를 인용하고, 자료가 없으면 지어내지 않고 보류하는 **서버 모듈 전체**를 만들었습니다(코드 약 8,800줄, 테스트 243개). 실제 DB·로그인·서버 배포·외부 생성 API·PDF/HWPX 파싱은 **연결 지점만 만들고 구현하지 않았습니다**.
2. **중학생 표현 100문항 실험**: 같은 저장소·같은 권한 필터·같은 검색기를 쓰는 조건에서,
   - **RAG만**(검색 1위 문서를 그대로 답으로 사용): **12/100**
   - **현재 엔진(보완 전)**: **60/100**
   - **현재 엔진(유사어 보완 후)**: **87/100**
   - 다만 보완에 쓰지 않은 test 절반에서는 **29 → 32/44(+3문항)** 에 그쳤습니다. 처음 보는 표현에 약하다는 것이 가장 큰 문제입니다.
3. **사전 문서**: 가상 학원 3곳의 운영 문서 36개와 원생 리포트 48개(총 84개), 정형 사실 645개, 평가 질문 90개, 중학생 표현 질문 100개를 준비했습니다. 제공받은 지시서·기술 조사·프로젝트 기준·합성 평가자료 81건도 함께 썼습니다.
4. **문제점**: 규칙 사전에 의존해 새로운 말투에 약합니다. 평가 자료를 직접 만들고 그 자료로 다듬었기 때문에 독립 평가가 아닙니다. 운영 연동(DB·인증·배포·생성 API)도 하지 않았습니다.

## 1. 개발 범위

### 1.1 무엇을 만들었나

질문을 받으면 아래 순서로 처리하는 **독립 서버 모듈**(`src/features/rag-consultation/server`)입니다. 표준 `Request → Response` 핸들러라서 정해지지 않은 백엔드에 붙일 수 있습니다. 현재 앱은 정적 export여서 앱 안에 서버를 둘 수 없습니다.

```text
요청 검증 → 서버 세션으로 권한 범위 계산
 → 질문 해석(규칙): 학생·반·단원·기간·금액·부정/비교 표현·보안 신호
 → 보안 차단: 다른 학원·전체 학생 명단·권한 밖 학생 → 거부
 → 학원 정보: 수강료·시간표·강사·모집·휴보강 = 정형 사실 조회(생성 0회)
              환불·셔틀·시설 등 = 승인 문서의 해당 절·표 칸 인용(생성 0회)
 → 학습 분석: 정답률·취약 영역·기간 비교·월말 평가(생성 0회), 원인·태도·예측 요청은 보류
 → 학습 방향: 강사가 확인한 학습 방향이 있으면 인용, 없을 때만 생성 1회(장애 시 담당자 연결)
 → 사후 검사: 인용 재확인, 답변 숫자가 근거에 있는지, 다른 학생 이름·코드가 섞이지 않았는지
```

### 1.4 구현하지 않은 것(범위 밖 또는 차단 요소)

- **운영 DB·로그인 연동·서버 배포**: 저장소에 대상이 없습니다. 지금은 메모리 저장소라서 재시작하면 색인이 사라집니다.
- **외부 생성 API 실연동**: 키와 공급자가 정해지지 않아 **검증하지 않았습니다**. 테스트는 mock으로만 했습니다.
- **PDF·DOCX·HWPX·스캔 파싱**: 현재는 텍스트/Markdown 표만 읽습니다.
- **임베딩·벡터 DB·리랭커·GraphRAG 등**: 기술 조사의 P1·P2 항목입니다. 서버 자원이 확인되지 않았고 효과를 비교할 실제 데이터가 없어 보류했습니다.

## 2. 중학생 유사어 100문항: RAG만 vs 현재 엔진

### 2.1 질문 세트

- 파일: `server/__fixtures__/academies-v1/eval/middle-school-paraphrase.jsonl`
- **100문항**: 답할 수 있는 질문 85개 + 문서에 없어서 보류해야 하는 질문 15개
  - 학원별: 가온수학 55개 · 새솔영어 45개(다온입시는 고등부라 제외)
  - 계정: 중학생 3명, 비회원 방문자 2명
  - 기준일: 2026-11-02 ~ 11-20
- **16개 유형**: 수강료 12, 시간표 11, 정답률 10, 휴보강 9, 강사 5, 취약 영역 5, 셔틀 5 외
- **유사어 107개**를 섞었습니다. 문서의 공식 표현 대신 중학생이 실제로 쓸 법한 말입니다.
  - 학원비·원비·깎아줘, 쌤·샘·담당샘
  - 보충(=보강)·학원 쉼·노는 날, 공부방·자습하는 방
  - 봉고·학원 버스, 레테·들어가기 전에 보는 시험, 몇 퍼·월말 시험, 족보·카톡
- **함정도 넣었습니다**: 채점 수정본(r1→r2), 아직 적용 전인 변경 시간표, 2027년 개정 수강료, 셔틀 1회차/2회차 열 혼동, 아직 발행되지 않은 11월 리포트, 미승인 초안 금액.
- **작성 방식**: 엔진 코드를 보지 않고 학원 문서만 보고 작성했습니다. 작성 후 스크립트로 확인한 내용은 두 가지입니다.
  - 모든 정답 문구가 해당 문서에 실제로 있는지
  - 정답 문서가 그 날짜에 승인·유효하고, 리포트는 본인 것인지
  - 사람 검수와 실제 학생 질문 수집은 하지 않았습니다(2.7 한계).

### 2.2 비교 방법(공정 조건)

세 방식 모두 **같은 저장소, 같은 권한·승인·유효기간 필터, 같은 BM25 검색기**를 씁니다.

| 방식                      | 내용                                                                                         | 맞았다고 보는 기준                                                                                           |
| ------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **A. RAG만**              | 질문 원문으로 상위 3개 청크 검색 → **1위 청크 원문**을 답으로 사용. 생성 모델·보류 기능 없음 | 1위 청크가 정답 문서이고 정답 문구를 모두 포함하며 금지 문구가 없음. 보류 질문은 검색 결과가 0개일 때만 정답 |
| A′. 참고 상한             | "상위 3개를 읽고 완벽하게 답하는 생성 모델이 있다면"을 가정                                  | 상위 3개 중 정답 문서 청크에 정답 문구가 모두 있음                                                           |
| **B. 현재 엔진(보완 전)** | 위 1.1의 전체 흐름                                                                           | 상태 `answered` + 정답 문구 전부 + 금지 문구 없음 + 정답 문서 인용. 보류 질문은 답하지 않음                  |
| **C. 현재 엔진(보완 후)** | B에 유사어·라우팅 보완(2.5)을 더함                                                           | B와 같음                                                                                                     |

**과적합을 막기 위한 장치**

- 결과를 보기 전에 문항 ID의 해시(sha256)로 **dev 56개 / test 44개**를 나눠 고정했습니다.
- 사전 보완은 **dev 실패만 보고** 했고, test는 보완 후 성능 확인에만 썼습니다. 따라서 **test 결과가 일반화 성능에 가까운 값**입니다.
- 채점 보정 3건(MS-014·057·071)에는 `also_valid_source_ids`를 추가했습니다.
  - 질문 작성자가 결과를 보기 전에 notes에 "같은 문구가 다른 문서에도 있음"이라고 적어 둔 경우입니다.
  - 세 방식에 똑같이 적용했습니다.
- 채점 방식(대체 출처, A′ 지표)은 첫 실행 뒤에 확정했습니다. 그래서 **보완 전 엔진을 그대로 되돌려(git stash) 최종 채점 방식으로 다시 측정**했습니다.

### 2.3 결과

| 방식                                 | 전체 100 | 답할 수 있는 85 | 보류해야 하는 15 | dev 56 | **test 44** |
| ------------------------------------ | -------: | --------------: | ---------------: | -----: | ----------: |
| A. RAG만                             |   **12** |      12 (14.1%) |                0 |      3 |           9 |
| A′. 참고 상한(완벽한 생성 모델 가정) |        – | 최대 31 (36.5%) |        측정 불가 |      – |           – |
| B. 현재 엔진(보완 전)                |   **60** |      51 (60.0%) |                9 |     31 |      **29** |
| C. 현재 엔진(보완 후)                |   **87** |      73 (85.9%) |               14 |     55 |      **32** |

- **검색 자체의 품질**(85문항 기준): 정답 문서가 1위인 비율 37.6%(32개), 3위 안에 있는 비율 62.4%(53개).
- **학원별**: 가온 5 → 33 → 48 / 55, 새솔 7 → 27 → 39 / 45.

**해석**

- **A → B (+48)**: 차이는 대부분 "검색 다음 단계"에서 나왔습니다.
  - "우리 반"을 서버가 아는 학생의 반으로 바꾸는 정형 조회: BM25만으로는 "우리 반"이 어느 반인지 알 수 없습니다.
  - 표에서 질문한 칸만 고르는 기능
  - 자료가 없을 때 보류: RAG만은 15개 모두 무언가를 답해 0점입니다.
  - 상위 3개를 완벽하게 읽는 생성 모델을 가정한 A′도 답할 수 있는 85개 중 **최대 31개**입니다. 검색 결과만으로는 B(51개)에도 못 미칩니다.
- **B → C**: dev는 31 → 55로 크게 올랐지만 이 값은 보완에 쓴 문항이라 성능 지표가 아닙니다.
  - 보완에 쓰지 않은 **test는 29 → 32(+3, 65.9% → 72.7%)**: 고쳐진 3개, 새로 틀린 0개입니다.
  - 기존 회귀 테스트 243개(합성 81건, 가상 학원 90건 포함)도 그대로 통과합니다.
  - 다만 3개 대 0개는 표본이 작아 **통계적으로 유의하다고 말할 수 없습니다**(부호 검정 단측 p≈0.125).
  - test 정확도의 95% 신뢰구간도 대략 ±13%p입니다.

보완 전 엔진이 RAG만보다 **오히려 나빴던 유형**도 있습니다.

- **휴강·보강(1 vs 3), 보강 규정(0 vs 1)**: "보충"을 학습 상담 요청으로 잘못 분류해 엉뚱한 성적 리포트를 답했습니다.
- **학습 방향(0 vs 1)**: "쌤이 뭐 하라고 했어?"를 정답률 질문으로 처리했습니다.

규칙 엔진은 말투를 잘못 읽으면 검색보다 더 크게 틀릴 수 있다는 뜻입니다.

### 2.7 한계

- 질문은 문서를 보고 **AI가 작성**했습니다. 실제 중학생 질문 로그도 아니고 사람이 검수하지도 않았습니다. 실제 분포와 다를 수 있습니다.
- A(RAG만)에는 생성 모델이 없습니다. 실제 생성 모델을 붙이면 A′ 상한(답할 수 있는 85개 중 최대 31개)까지 오를 수 있지만, 근거 없는 답(환각)도 생길 수 있습니다. 키가 없어 **측정하지 않았습니다**.
- 학원 2곳·100문항(test 44개)은 작은 표본입니다. dev 98%와 test 73%의 차이가 "사전에 넣은 표현만 잘 맞힌다"는 점을 보여 줍니다.

재현 방법:

```bash
node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON src/features/rag-consultation/server/eval/paraphrase-eval.ts 2-after
```

결과 파일은 `server/__fixtures__/academies-v1/eval/results/`에 있습니다. `1-before.json`은 보완 전 엔진, `2-after.json`은 보완 후 엔진의 결과이며 문항별 답변 전문이 들어 있습니다. 한 문항만 확인하려면 `server/eval/debug-query.ts MS-072`를 실행합니다.

### 4.2 문제점(중요한 순서)

1. **처음 보는 말투에 약합니다.** 주제 판별이 규칙 사전에 의존합니다.
   - 보완에 쓴 dev는 98%, 쓰지 않은 test는 73%입니다.
   - "깎아줘", "내려줘요", "들어가기 전에 보는 시험"처럼 사전에 없는 표현은 매번 사람이 추가해야 합니다.
   - 사전이 커질수록 표현끼리 겹치는 문제도 늘어납니다. 예: "들어갈 수"가 모집 주제와 입실 시간 양쪽에 걸립니다.
2. **잘못 읽으면 크게 틀립니다.** 보완 전에는 "보충"을 학습 상담으로 오인해 엉뚱한 성적 리포트를 답했습니다(휴보강 유형에서 RAG만보다 나쁨). 보류 장치는 "근거 없음"은 막지만 "다른 질문으로 오해한 답"은 막지 못합니다.
3. **과잉 보류가 있습니다.** "뭐 때문에 깎였어요?"처럼 리포트에 답이 있는 질문을 원인 추정 요청으로 보고 보류합니다.
4. **평가가 독립적이지 않습니다.**
   - 문서·질문·정답을 이 작업에서 만들었고, 그 실패를 보며 규칙을 다듬었습니다.
   - 가상 학원 90건은 전부, 100문항은 dev 절반을 보완에 썼습니다.
   - 실제 학생 질문도 아니고 사람 검수도 없습니다.
5. **답변이 길거나 엄격 기준에서 넘칩니다.** 표 칸 선택이 불완전합니다(셔틀 1·2회차를 함께 표시). 관련 추가 안내(적용 예정 변경)를 덧붙이는 경우도 있습니다.
6. **운영 연동을 하지 않았습니다.**
   - 메모리 저장소(재시작 시 소실, 다중 인스턴스 호출 제한 미지원)
   - DB·로그인·서버 배포 없음
   - 생성 API 실연동 미검증
   - PDF/HWPX 미지원
7. **이름 인식이 제한적입니다.** 강사 이름은 "○○쌤" 패턴으로만 인식합니다. 원생 이름은 서버 명부에 의존하고, 2글자 이름은 앞뒤 글자 조건으로만 판별합니다.

### 4.3 제안

1. **실제 질문 로그로 사전 보강 루프를 돌립니다(운영 절차, 우선).**
   - 보류·담당자 연결이 된 질문을 주 1회 검토해 사전에 추가합니다.
   - 추가 전후를 고정된 test 세트로 비교합니다. 이번 실험의 dev/test 분리 방식을 그대로 쓰면 됩니다.
2. **질문 정규화 단계 도입을 실험합니다(기술 조사 P1).**
   - 사전으로 주제를 못 정한 질문만 대상으로 합니다.
   - (a) 로컬 임베딩 기반 주제 분류, 또는 (b) 가명 처리 후 생성 모델 1회로 공식 표현 재작성을 붙여 봅니다.
   - 이번 100문항 test 절반에서 32/44보다 오르는지, 오분류가 늘지 않는지 확인한 뒤 채택합니다.
3. **평가를 독립적으로 다시 합니다.** 실제 중학생·보호자 질문을 수집하고, 사람이 정답을 검수하고, 처음 보는 학원 자료로 다시 측정합니다.
4. **답변 간결화**: 질문한 학생의 학년에 맞는 열만 고르기(초등/중등), 적용 전 변경은 "예정"으로 분리 표시하거나 생략할지 팀이 정합니다.
5. **운영 연동**: 실제 DB·로그인 정보로 포트(`AccessScopePort`, `ApprovedFactsPort`, `RagDocumentsPort`)를 구현합니다. 그다음 생성 공급자의 약관(미성년 이용·국외 처리)을 검토하고, 실제 문서 형식(PDF/HWPX) 비율을 확인합니다.
